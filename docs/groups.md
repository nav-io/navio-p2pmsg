# Groups

Decision 30: sender-keys with epoch rotation. Designed so the group state
machine can be swapped for MLS later without changing the chat schema above it.

## The trap this avoids

The obvious design — a public topic plus a symmetric group key — leaks the
group. BROADCAST scope encrypts the ECIES layer to the generator point, so
*anyone* on the bus decrypts it and reads the `topic` field of the USER_DATA
frame. Content stays secret; the group's identifier, its size in traffic terms
and its complete activity timeline do not.

So a group message is ECIES'd to a **member-only group key**. The bus already
supports this: the key registers as a session key and falls out of the existing
trial-decrypt path, with no changes to `bus`.

## Key schedule

Per group, per epoch, everything derives from one secret:

```
epoch_secret(e)            32 B, random at epoch 0, rotated by an admin
  ├── group_ecies_sk   = HKDF(epoch_secret, info="group/ecies") mod q
  ├── group_fmd_root   = HKDF(epoch_secret, info="group/fmd/" ‖ u32le(i))
  └── content_key      = HKDF(epoch_secret, info="group/content")
```

- `group_ecies_sk` — envelope encryption. One envelope per message, one proof
  of work, regardless of member count. This is the whole reason for a group
  key rather than fan-out.
- `group_fmd_root` — a **group-wide clue key**, so senders flag group messages
  to the group and any member's archive query retrieves them. Without this,
  offline delivery would not work for groups at all.
- `content_key` — symmetric layer under the ECIES layer. Redundant against an
  outsider, load-bearing against a *former member* who recorded ciphertext
  while a member: rotating the epoch changes it.

Sender authentication stays the existing per-message BLS signature from the
sender's device key, verified against the group's member list.

`group_id` = 32 random bytes, generated by the creator. Not derived from
membership, so it survives every membership change.

## Group state

Each member holds, and validates independently:

```
u8      version = 1
u8[32]  group_id
u32     epoch
CompactSize n
n × {
  u8[48]  identity_pub
  u8      role            0 member, 1 admin, 2 owner
  i64     joined_at
  u32     joined_epoch
}
CompactSize len, u8[len] name
CompactSize len, u8[len] topic_text
u8[32]  prev_state_hash                 // chains epochs together
u8[48]  author_identity                 // admin who produced this state
u8[96]  author_sig
```

State is a hash chain: `prev_state_hash` links each epoch to the last, so a
member can detect an admin presenting divergent histories to different members.
Members reject a state whose `prev_state_hash` does not match the state they
hold, and surface the conflict rather than silently picking one.

## Membership operations

Sent as chat frames of type `MEMBERSHIP`, signed by an admin.

| op | rekey? | notes |
|---|---|---|
| create | — | creator is owner |
| add | optional | rekeying on add stops the new member reading recorded history; default is **rekey**, so members join forward-only |
| remove | **required** | otherwise the removed member reads everything afterwards |
| leave | required if the leaver could read | self-initiated remove |
| promote / demote | no | role change only |
| rename / set topic | no | metadata only |

**Rekey** = admin generates `epoch_secret(e+1)` and delivers it 1:1 to each
remaining member over the ratchet (`ratchet.md`), then publishes the new group
state. That is O(n) small messages per rekey — fine at the group sizes this bus
carries, and the reason MLS exists for the sizes it does not. Rekey is batched
when several removals happen together.

A member who is offline during a rekey receives the new epoch secret when it
comes back, via the archive. Until then it sees undecryptable group traffic and
reports a gap; it must not silently drop it.

## Invites

Two flavours, because they have genuinely different security properties.

**Key-in-link** (default): the link *is* the secret.

```
navinv1…  (bech32m)
    u8      version = 1
    u8      network
    u8[32]  group_id
    u32     epoch
    u8[32]  epoch_secret
    i64     expires_at
    u8[48]  inviter_identity
    u8[96]  inviter_sig
```

Anyone holding the link joins instantly with no admin online. Anyone who
*sees* the link joins too — so it expires (default 24 h), and the group rekeys
when the invite expires or is revoked, which cuts off anyone who grabbed it but
never used it.

**Request-to-join**: the link carries `group_id`, `inviter_identity` and a
one-time token, but no secret. The joiner sends a request; an admin admits them
and delivers the epoch secret 1:1. Safe to post in a semi-public place, but
needs an admin online.

Applications should default to key-in-link for small private groups and
request-to-join for anything that might be forwarded.

## Limits

| limit | default | why |
|---|---|---|
| members | 256 | rekey is O(n) 1:1 messages, each with a proof of work |
| admins | 16 | |
| name / topic text | 128 / 512 B | |
| rekeys per hour | 12 | a rekey storm is a denial of service on every member |

## Interaction with the rest of v2

- **Archive.** Group messages carry the group clue key's flag. A member queries
  with the group detection key alongside its own; a rekey changes the group
  clue key, so a member must query with the detection keys of every epoch it
  needs to catch up on.
- **Multi-device.** Epoch secrets are account state and sync to all of a
  member's devices (`devices.md`).
- **Revoked devices.** Revoking a device rekeys every group it belonged to.
- **Ordering.** Group messages use the same causal DAG as 1:1 (`chat.md`).
  Concurrency is normal and expected; the DAG is what makes it legible.
